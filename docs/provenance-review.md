## 1. `buildHuffmanTable` vs LHa for UNIX `maketbl.c` の `make_table()`

もっともリスクが高いと見て、最初に照合した。

### 共通している点

- 「短い符号は直引きテーブル、長い符号は二分木」という**二段構えの復号構造**
- `table[]` と `left[]`/`right[]` という配列の持ち方

### 異なる点

| 観点 | LHa for UNIX `make_table()` | lhats `buildHuffmanTable()` |
|---|---|---|
| 先頭符号の算出 | `weight[i] = 0x10000 >> i` を使い、`start[i] += weight[i] * count[i]` で **16bit 固定小数点空間**に積む | `code = (code + count[len-1]) << 1` の**正準ハフマン漸化式** |
| `weight[]` 配列 | あり（中核をなす） | **無い** |
| 空きの表現 | `0`（内部ノード番号は `nchar` 以降の正数） | `-1`（内部ノードは `~nextNode` の**負数**） |
| 木の降下 | `unsigned short *p` の**ポインタ**を `&left[*p]` / `&right[*p]` で進める | **整数の節点番号**を `left[node]` / `right[node]` で辿る |
| ビット取り出し | `i & 0x8000` を見て `i <<= 1` と左シフト | `(c >>> bit) & 1` を見て `bit` を減らす |
| 進行の記録 | `start[k] = l` で表を書き換える | `nextCode[len]++` |
| `symLen` 相当 | 無い | あり（返り値に含む） |
| `left`/`right` の所有 | ファイルスコープの**グローバル配列** | 関数内で確保して**返す** |

### 判定

**独立実装である。**

先頭符号の算出方法が根本的に違う。`make_table()` の 16bit 固定小数点による
重み積算は特徴的な書き癖で、これが無い時点で転記ではない。番兵の取り方
（`0` と `-1`/`~node`）、木の辿り方（ポインタと添字）も一致しない。

共有しているのは「二段構えの復号表」という着想だけで、これは zlib の
`inflate_table` や JPEG のハフマン復号にも見られる教科書的手法である。

### Lhasa との比較

Lhasa (`lha_decoder` / `tree_decode`) は平坦な木配列を使う別の構造で、
lhats とも `make_table()` とも一致しない。どちらにも似ていないことが、
独立実装であることの傍証になっている。

### この照合で見つかった欠落（重要）

`make_table()` には CVE-2006-4335 / CVE-2006-4337 への対策として、
次の 3 つの検査が入っている。

1. `bitlen[i] > 16` の拒否
2. `(total & 0xffff) != 0` の拒否 — **Kraft 和が 1 でない符号表**（過剰購読・
   不完全）を弾く
3. 表添字が 4096 を超える場合の拒否

**lhats にはいずれも無かった。** 壊れた（あるいは細工された）書庫が不正な
符号長表を持っていた場合、TypeScript では型付き配列の範囲外書き込みが
黙って無視されるため、クラッシュはしないが**壊れた表ができ、結果として
黙って誤ったデータを返す**。これは本ライブラリが最も避けたい失敗の仕方である。

→ 対応済み。`validateCodeLengths()` を追加し、符号長の上限と Kraft 和を
検査して不正なら `LhaFormatError` を投げるようにした。

## 2. `decodeLh5` のブロック構造

`i === 2` のときの 2bit スキップ、符号長 7 以降の unary 拡張、
T シンボル 0/1/2 のランレングス意味論、位置シンボルから
`(1 << (sym-1)) + extra` を復元する規則。

これらはいずれも**フォーマットそのもの**であり、`Hacking_of_LHa` に
文書として記載がある。実装の表現ではなく仕様なので、一致するのが正しい。

**判定**: 問題なし。文書由来。

## 3. 定数

`NC=510`、`NT=19`、`NP=14/17`、`CBIT=9`、`TBIT=5`、`PBIT=4/5`、
`MAXMATCH=256`、`THRESHOLD=3`、辞書の `0x20` 初期化。

いずれもフォーマットが定める値であり、著作物性はない。

**判定**: 問題なし。

## 4. `-lh1-` (`src/lh1.ts`)

`Hacking_of_LHa` は「本書では当面、lh5, 6, 7 のことしか言及しない」と
明記しており、`-lh1-` の仕様書は手元の資料に存在しない。

そこで **`lzhuf.c`（吉崎栄泰 氏, 1988-11-20 / コメント英訳 奥村晴彦 氏,
1989-04-07）** が定義するアルゴリズムに基づいて実装した。`-lh1-` は
LHarc の作者自身による lzhuf を起源としており、`lzhuf.c` は自由な使用・
配布・改変が認められている。

パラメータが `Hacking_of_LHa` の記述と一致することを確認した。

| 定数 | lzhuf | Hacking_of_LHa の `-lh1-` |
|---|---|---|
| 辞書サイズ | `N = 4096` | dicbit = 12 → 4096 |
| 最長一致長 | `F = 60` | maxmatch = 60 |
| シンボル数 | `N_CHAR = 256 - 2 + 60 = 314` | （THRESHOLD=2 と整合） |

位置符号の静的表 `d_code` / `d_len` は、独立した 2 つの配布物から取得して
バイト単位で一致することを確認し、さらに 64 シンボルの完全な接頭符号
（Kraft 和 = 1.0）であることを機械的に検証してから採用した。

**LHa for UNIX の `dhuf.c` は参照していない。** 同ファイルは
`child/parent/block/edge/stock` を用いる Vitter 系のブロック管理で、
lzhuf の素朴な木更新とは構造が異なる。lhats は後者に基づいている。

**判定**: 問題なし。出典を NOTICE.md に明記済み。

## 結論

**NOTICE.md の記述は妥当である。**

- LHa for UNIX からのコード流用は無い（文書のみ参照）
- Lhasa からのコード流用は無い（外部検証ツールとしてのみ利用）
- `-lh1-` は lzhuf 由来であり、その旨を明記した

副産物として、`make_table()` が持っていた CVE 対策が lhats に欠けていることが
判明し、修正した。防御的なレビューが本来の目的以上の成果を出した形になる。
